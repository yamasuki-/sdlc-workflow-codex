# sdlc-workflow-codex

Codex で動く V 字モデルのソフトウェア開発ワークフローです。Excel・Word・PowerPoint・PDF・Markdown の要求資料から、要件、設計、実装、受入テストまでを進めます。工程ごとに機械チェックと独立レビューを行い、人の承認を記録してから次の工程に進みます。

移植元は [sdlc-workflow のコミット `9aceab437306`](https://github.com/yamasuki-/sdlc-workflow/tree/9aceab4373068ee5247c64d668e2fa9b494b75d2) です。

| 工程 | 主な成果物 |
|---|---|
| 00 取り込み | 出典付き SRC |
| 01 要求整理・分析 | REQ、曖昧・矛盾・欠落、質問 |
| 02 要件定義 | SR、NFR、受入・システムテスト仕様 AT |
| 03 基本設計 | BD、IF、結合テスト仕様 IT |
| 04 詳細設計 | DD、単体テスト仕様とコード、Red の証跡 |
| 05 実装 | コード、Green の証跡、セキュリティレビュー |
| 06 結合テスト | IT の実装と実行結果 |
| 07 システム／受入テスト | AT の実装と実行結果、要件カバレッジ |

- `$sdlc-init` で初期化し、`$sdlc` で開始・再開します。
- `$defect` は不具合対応、`$change` は承認済み仕様の変更要求に使います。どちらも人の承認後に対象工程から差分をやり直します。
- 承認済みの設計で判断できない振る舞いは未解決事項として記録し、人の回答と設計への反映を待ちます。

## クイックスタート

Python 3.10以上、Git、Bash、hooks とサブエージェントが使える Codex CLI を用意します。導入先は既存または新規の Git リポジトリです。

```bash
git clone https://github.com/yamasuki-/sdlc-workflow-codex.git
cd sdlc-workflow-codex
python -m pip install -r requirements.txt
python install.py --project /path/to/project
cd /path/to/project
codex
```

1. Codex でプロジェクトを信頼し、`/hooks` で SDLC の hooks を確認・承認します。
2. Codex に「`$sdlc-init` で初期化してください」と依頼し、言語・テストコマンドなどを設定します。
3. `input/` に要求資料を置き、「`$sdlc` で進めてください」と依頼します。
4. 工程ゲートで停止したら、成果物とレビューを確認します。Codex の外の対話端末で `scripts/approve 00` を実行し、承認記録をコミットします。再度 `$sdlc` を依頼すると続きから進みます。

ユーザー共通配置、Windows での操作、更新、トラブルシュートは [USAGE.md](USAGE.md) を参照してください。

## 工程の進み方

計画 → タスク分解 → 実行 → 統合・機械チェック → 独立レビュー → 人の承認

タスク間の依存関係と担当ファイルを記録し、競合しないタスクを最大2件まで委譲します。作業ツリーを指定できない環境では逐次実行します。工程とタスクの進捗は `state/` に記録されるため、中断後も再開できます。

| 確認項目 | 仕組み |
|---|---|
| 機械チェック | `scripts/sdlc check` がトレーサビリティと `project.yaml` のチェックを実行。MUST の失敗は工程の進行を止める |
| 独立レビュー | 成果物の作成者と別のサブエージェントが工程別チェックリストでレビュー。実装工程ではセキュリティレビューも実施 |
| 人の承認 | `scripts/approve` が対話端末で承認・条件付き承認・差戻しを記録。承認時の成果物ハッシュで有効性を確認 |
| TDD | 工程04で単体テストを作って Red の証跡を取り、工程05で実装と Green の証跡を残す |
| 編集ガード | `apply_patch` の編集先を検査し、前工程が未承認の成果物や承認済み成果物への書き込みを拒否する |

hooks は Codex で有効化と承認が必要です。シェル経由の編集の検出には限界があるため、適用範囲は [USAGE.md のガードの説明](USAGE.md#4-ガードと適用範囲) を参照してください。

## 不具合と変更要求

| 依頼 | 使うスキル | 承認前に確認すること |
|---|---|---|
| 承認済み仕様と実際の動作が違う | `$defect` | 再現テスト、原因、混入・流出工程、影響範囲、対応案 |
| 承認済み仕様を変える、機能を追加する | `$change` | 現行仕様・実装への影響、対応案、やり直しの開始工程 |

人が対応案と影響範囲を承認すると、対象の工程から差分をやり直します。承認済み設計で決まっていない動作は、推測で補完せず、根拠となる箇所と質問を記録して人の判断を待ちます。

## ファイル構成

| 配置先 | 内容 |
|---|---|
| `.agents/skills/` | 初期化、工程実行、不具合・変更要求のスキル |
| `.codex/agents/` | 分析、設計、テスト、実装、レビューなどの役割定義 |
| `.codex/sdlc/` | CLI、全体ルール、テンプレート、工程別チェックリスト |
| `.codex/hooks.json` / `.codex/hooks/sdlc/` | Codex の hook 設定とガード |
| 対象プロジェクトの `AGENTS.md` / `project.yaml` | ルールの参照、テストコマンド、工程別チェック設定 |
| 対象プロジェクトの `input/` / `docs/` / `state/` / `rules/` | 入力資料、工程成果物、承認・進捗記録、プロジェクト固有ルール |
